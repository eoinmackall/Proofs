Verification

There are two questions to ask about a lemma: “Who checked this argument?” and “Can I still rely on what it cites?” A certificate answers the first; Proofs follows the citations to answer the second. Verification here means review of a written argument by a language model, not a formal proof checked by a kernel. You can read the argument and have your own model challenge it.

Certificates & Merkle Hashes

A lemma ID stays the same across repairs. A Merkle hash identifies the particular argument the verifiers reviewed. Proofs computes it from the files rather than trusting a stored “verified” flag. Schematically, the inputs are: 

SHA-256({
  statement_hash,                    # whitespace-normalized statement
  proof_hash,                        # whitespace-normalized proof
  sorted_cited_statement_hashes,     # cited lemmas' statements + cited references' formal statements
  computations                       # script hashes, languages and recorded RESULTs
})
  • What a citation pins: Suppose the parity proof cites “the square of an odd integer is odd.” Replacing the proof of that lemma changes its own hash, but the parity proof still uses the same statement. Its certificate need not change. Narrow the cited statement to positive odd integers, though, and the parity proof must be checked again: it claimed to cover negative integers too.
  • What a certificate records: After all verifier steps accept, the verifying run records the lemma ID, hash, contributor, model, and date. A certificate counts only if its hash still matches. One acceptance is one complete round of review, not one vote per verifier prompt.
  • What gets saved: A run stores any cited scripts and the certificate before appending the accepted lemma. A collaborator can therefore inspect the argument and its evidence together.

Stochastic Citation Rechecks

Reviewing every earlier proof on every citation would mean doing the same work repeatedly. Instead, before saving a model-written proof that passed review, proofs run samples each distinct lemma it cites directly. With the default base of 2, a cited lemma with one acceptance has a 1/2 chance of another check; after two acceptances, 1/4. In general the chance is p−d, where p is the configured base and d counts acceptances for the current hash. This is a chance of being checked, not an estimate of mathematical correctness.

  • Set run.citation_recheck_base in local settings, or pass --citation-recheck-base 1 to select every direct lemma citation. Use -1 to turn sampling off. References from the literature are not sampled.
  • If a recheck rejects a proof, the refutation is against the cited lemma. Proofs still saves the new proof, but suspends it and every other lemma that depends on the refuted result. If the verifier gives no verdict, the run pauses instead; resuming retries the missing check.
  • Rechecks do not cascade transitively and do not automatically re-execute scripts; for a complete dependency audit, run proofs verify DIR LEMMA_ID --full.

Refutations & Suspension

A verifier’s rejection of a draft is feedback for the reviser. Rejection of a stored proof by verify, repair, or a citation recheck writes a refutation under the conjecture’s refutations/. Read it to see which step was challenged and why. It objects to this proof, not necessarily to the truth of the statement. If the hash changes, the objection goes stale; later verifiers can still read the reason.

A suspended lemma is still in the files. You can inspect or repair it, but planners and provers cannot build on it. Proofs computes suspension when it reads the graph. Any of the following is enough:

  • It holds no valid certificate (uncertified).
  • A refutation matches its current hash (refuted).
  • It has conflicting fork versions or lies on a citation cycle.
  • It cites a missing reference, a missing lemma, or any suspended lemma.

A lemma can therefore have a valid certificate and still be suspended. If the odd-square lemma is under challenge, the parity proof that cites it is unusable until that challenge is resolved. There is no “suspended” flag to edit by hand.

Verify, Repair, Prune & Status

Start with status. Replace LEMMA_ID below with an ID from your run log or exported graph, such as alice/3f9a2c1b4d5e6f70/7d1e90. Status makes no model calls and changes no files. It shows dependencies first, so if a lemma is suspended only because of a citation, look earlier in the output for the underlying objection. Repairing that dependency can make the citing lemma usable again without another check of its own proof. 

proofs status parity LEMMA_ID

Use verify for a new opinion on the stored proof. Use repair when there is already an objection: it presents the objection to the verifiers and, if they uphold it, attempts a new proof under the same ID. Both commands need a model route or backend flags. Choose the action that matches what you found:

  • proofs verify parity LEMMA_ID checks just that argument. Add --full to check everything it relies on, dependencies first, stopping at the first rejection. --parallel 3 runs up to three verifier checks on each lemma at once.
  • proofs verify parity --uncertified works from the roots up on lemmas missing a valid certificate. It skips those blocked by a still-suspended dependency.
  • proofs repair takes the path to a particular refutation JSON file. Alternatively, proofs repair --all parity tries the current refutations in dependency order. A repair that changes a statement also revisits affected proofs above it.
  • Reviewing a computation normally means reading the saved script and result. To reproduce a cited Python script on a conjecture with Python declared, use proofs verify parity LEMMA_ID --tools python --run-code. You see the script and must confirm before execution; see the computation contract.

proofs prune parity is cleanup, not a way to fix a proof. It removes still-refuted lemmas, compacts repaired versions and duplicate certificates, and clears stale scratch files. Normally, lemmas that cited a removed one stay in the graph, suspended. --with-dependents deletes those lemmas too. Commit or back up the workspace first if you want to retain that history.

Exit Codes for Automation

For verify and repair, 0 means the requested checks completed without a failure, 1 means a proof was rejected or a repair failed, and 3 means a verifier gave no verdict. A missing reply does not create a refutation; an outage is not evidence against a proof.
