Collaboration

Share the workspace, not the Proofs installation. Git carries the conjecture, lemmas, and reviews between collaborators; there is no central proof database. You can use a different model from the person who started a conjecture and pick up from their accepted results.

Distributed Design

Suppose Alice proves that an odd integer has an odd square. After Bob pulls her files, his next run can cite that lemma by its ID. He doesn’t need her model, checkpoint, or terminal session. Three things make this possible:

  • Stable names: Each ID includes a contributor, a run, and six hex digits, for example alice/3f9a2c1b4d5e6f70/7d1e90. It means the same lemma in every clone; Bob doesn’t renumber Alice’s results when he adds his own.
  • Separate writers, one graph: Each run appends to its own files. At startup Proofs reads all runs for this conjecture into one graph, then adds its own new results. A running process doesn’t see another process’s writes live. Stop, pull, and resume to pick up new work.
  • Checkable evidence: Certificates name the reviewer and model. Every clone with the same files computes the same suspension state; nobody has to merge a “solved” flag. For another opinion, Bob can run proofs verify parity LEMMA_ID --full with his own model.

Git-Coordinated Append-Only Streams

Starting a shared project: From the workspace root, initialize Git if needed and commit the marker, ignore rules, and conjecture. For the quickstart workspace, that first commit could be: 

cd ~/my-proofs
git init
git add .proofs .gitignore conjectures/parity
git commit -m "Start the parity conjecture"

Push this repository to a remote you control using ordinary Git. A collaborator clones that repository and changes into it. The committed .proofs already makes the clone a workspace. Bob sets his identity once with proofs config --global user.id bob and supplies his own model flags or routes. Running proofs init at the root will create the ignored local settings template if it’s missing.

Adding results: On a branch tracking the shared remote, pull before you start. Here parity has a default model route configured. After the run stops, inspect what you’re about to share; Proofs never commits, pushes, or pulls for you. 

git pull
proofs run parity --max-iterations 3
git add conjectures/parity
git diff --cached --stat
git commit -m "Add parity lemmas and certificates"
git push

The marker and ignore rules live at the workspace root. Inside a conjecture directory, share the mathematical records, not the files needed only to resume a particular process:

A stream is a sequence of JSON Lines files: each starts with a header naming the contributor and run, followed by one record per line. Two contributors normally add different files, so Git can keep both. Maintenance is the exception: prune rewrites streams. Coordinate pruning with other writers. If a merge leaves a conflict marker in a stream, Proofs stops and names the file and line rather than guessing which records to keep.

Reproofs & Fork Resolution

What if Alice and Bob both repair the same lemma before seeing the other’s change? If both write a new proof, each repair appends a reproof under the original lemma ID in the repairer’s own stream. Its supersedes field names the version it replaces. Git may merge both files cleanly, yet the lemma now has two successor versions. This is a fork in the lemma’s history, not a Git branch. Proofs compares the statements rather than preferring the last writer:

  • Agreeing statements: if the latest versions differ only in their proofs or in whitespace, any certified version can represent the lemma. If several qualify, the smallest lemma hash breaks the tie. proofs prune keeps the winning certified version and drops the rest.
  • Conflicting statements: If one successor weakens the hypotheses while the other keeps them, a citation to the ID is ambiguous. Proofs suspends the lemma, reports the conflicting file and line locations, and leaves them alone even during pruning. Review the statements together, keep the intended version, and commit the resolution before building on it.
