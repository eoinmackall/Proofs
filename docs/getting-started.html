Guide

Getting Started

Proofs works in a workspace, much like Git works in a repository. You install the proofs command once; each workspace is a separate directory for your conjectures and the arguments the models build. Here you’ll state a small conjecture about even numbers, run one iteration, and learn where to find the result.

Quickstart

Use a terminal on Linux or macOS, or a Linux shell inside WSL 2 on Windows. See Installation if you need to set one up. Choose one of the following ways to get the CLI. Either works with local and hosted models; neither downloads a model or starts a server.

With Nix and flakes enabled, open a shell that has Proofs and its dependencies on PATH. No clone is needed. Run the remaining commands in that shell; enter it again for a later session.

nix develop github:eoinmackall/proofs

With Git and Python 3.9 or newer, install from the source checkout into a virtual environment. In a later session you only need to repeat the activation line, not the clone or install.

git clone https://github.com/eoinmackall/proofs.git "$HOME/proofs-src"
python3 -m venv "$HOME/.venvs/proofs"
. "$HOME/.venvs/proofs/bin/activate"
python -m pip install "$HOME/proofs-src"

Check that proofs --help lists the commands. Now choose a contributor ID (replace alice with yours) and create a workspace outside the program checkout. The ID is a one-time setting: it becomes the first part of every lemma ID you contribute. 

proofs config --global user.id alice
proofs init ~/my-proofs
cd ~/my-proofs
proofs new parity

The new conjectures/parity/conjecture.md is empty. Write a statement with explicit hypotheses and a conclusion, not a prompt asking for a solution. You can use your editor, or fill the new file like this: 

printf '%s\n' 'For every integer n, if n^2 is even then n is even.' > conjectures/parity/conjecture.md

Choose one endpoint for the run. If you already have a local model server, substitute its API base URL and the model name it serves. This example assumes the server is reachable from this shell: 

proofs run parity --host http://localhost:8080/v1 --model qwen3-32b --max-iterations 1

Alternatively, use a hosted endpoint. For OpenAI, first set OPENAI_API_KEY in your shell environment and choose a model your account can use. The provider receives the prompts and may charge for the calls: 

proofs run parity --host https://api.openai.com/v1 --model gpt-5 --api-key "$OPENAI_API_KEY" --max-iterations 1

One iteration tries a lemma; it can take several model calls and need not settle the conjecture. If nothing was accepted, repeat the command with a higher limit to continue. Without a limit the run can keep going until settlement; press Ctrl-C once to pause and save your place.

A commit message with a lemma ID means there’s an argument to read. The proof lives under conjectures/parity/dags/ and its review record under conjectures/parity/certificates/. To read the proof alongside the lemmas it cites, export the graph: 

proofs export parity -o out --format html

Open out/proof.html in your browser and select a dot to read its proof. Export reads local files; you don’t need another model call. The example on the home page shows what the same export looks like after many runs.

Installation

The shell commands in this guide use Unix paths. Prepare your platform first, then use the Nix or pip tab in the Quickstart. SageMath and a code sandbox are optional; neither is needed for a text-only proof.

  • Linux: Use your usual terminal. The Nix shell supplies Python and, on Linux, bwrap (bubblewrap) for optional code execution. For pip, install Git and a Python 3.9+ interpreter with virtual environment support; on a recent Debian or Ubuntu system, sudo apt install git python3 python3-venv supplies these. Install bubblewrap separately if you later enable --tools.
  • macOS: Use Terminal. The Nix flake has Intel and Apple Silicon targets. For pip, check git --version and python3 --version; install the Command Line Tools (xcode-select --install) for Git if needed, and a current Python for macOS if yours is too old. Optional script execution uses sandbox-exec, not bubblewrap; see the limits of the macOS sandbox before enabling it.
  • Windows: Use Windows Subsystem for Linux (WSL 2). On a recent Windows system, run wsl --install -d Ubuntu in PowerShell as Administrator, restart if prompted, then open Ubuntu. Follow the Linux instructions inside Ubuntu, including installing Nix or Python there. Keep the workspace in your Linux home (e.g. ~/my-proofs), not under /mnt/c. Native Windows lacks the Unix file locks Proofs uses to protect active runs and has no supported code sandbox.

With Nix: Use the Nix installer for your platform if Nix is not already installed. If nix develop reports disabled features, use nix --extra-experimental-features 'nix-command flakes' develop github:eoinmackall/proofs. From a source clone, plain nix develop uses the local flake. To run one command without entering a shell, use nix run github:eoinmackall/proofs -- --help.

With pip: The base install includes requests, rich, and orjson. From the source checkout in the activated environment, python -m pip install '.[fast,png]' also installs NumPy for the breadth strategy and matplotlib for PNG export; HTML export needs neither. To try a checkout without installing it, an environment with Python 3.9+ and requests can run PYTHONPATH="$HOME/proofs-src" python3 -m proofs --help.

Workspaces

Where Git looks up the directory tree for .git, Proofs looks for a marker file named .proofs. That directory is the workspace root. The two markers are independent: proofs init doesn’t run git init, and a local proof needs no Git repository. If you want history or collaborators, put the workspace under Git, not your installed copy of Proofs.

A workspace can hold many conjectures. A bare name such as parity means conjectures/parity under the root, even if you run the command from a subdirectory. A path is relative to your shell as usual: from inside conjectures/parity/, proofs run . targets the same conjecture as proofs run parity. Outside the workspace, give the path to the conjecture directory or change back into the workspace before using a name.

  • Once per workspace: proofs init [DIR] creates the root (current directory if omitted), the .proofs marker (format = 2), conjectures/, and a gitignored .proofs-local.json for this machine. Running it again at the root keeps your settings and conjectures and refreshes only the managed block of .gitignore. Don’t initialize a second workspace inside the first.
  • Once per problem: proofs new NAME creates a new directory with an empty conjecture.md. This is the only file you need to fill in. comments.md is for private hints; references/ and references.md (initially []) are for source material and citable results. The rest of the directory layout fills in as the run produces results.

Your contributor ID is a Proofs setting, not your Git login. proofs config user.id prints it. You can also set a name and email. The settings file is in ~/.config/proofs/config (or $XDG_CONFIG_HOME/proofs/config), outside every workspace, but the identity you supply is recorded in the headers of the result files you share: 

proofs config --global user.name "Alice Example"
proofs config --global user.email alice@example.com

Backends & Routing

A backend is how Proofs talks to a model; a route says which model handles a job, such as writing a proof or checking one. Start with one model for all jobs. The model options for run also work on parse, verify, and repair. Reading the graph with status or export needs no backend.

Single-model CLI usage

For an OpenAI-compatible service (including llama-server, vLLM, OpenRouter, and Gemini’s compatibility endpoint), give --host the API base URL including its version path. Proofs appends chat/completions; don’t append that yourself. --model names an already served model. Choose the command for your provider: 

# Local llama-server with the alias qwen3-32b
proofs run parity --host http://localhost:8080/v1 --model qwen3-32b
# Hosted OpenAI model; pass the key from the shell
proofs run parity --host https://api.openai.com/v1 --model gpt-5 \
  --api-key "$OPENAI_API_KEY"
# Native Anthropic Messages API; --host defaults to https://api.anthropic.com
proofs run parity --backend anthropic --model claude-opus-4-6 \
  --api-key "$ANTHROPIC_API_KEY"
  • Choosing the protocol: Leave the backend on auto for most OpenAI-compatible servers. Proofs probes /props to recognize llama.cpp; otherwise it uses standard OpenAI fields. If a proxy hides the probe, select --backend llamacpp or --backend openai yourself. Select anthropic explicitly for the Messages API.
  • Reading the record: The saved model name can differ from the name you requested. Proofs records the weights filename reported by llama-server or the model ID reported by a hosted service, using the requested name if the server reports none.
  • Tuning calls: Start with the server’s defaults. Use --effort only with a level supported by your model, and --temperature only on non-Anthropic backends. See CLI Flags for the options.

Role-based model routing (.proofs-local.json)

To stop retyping flags, edit the workspace’s .proofs-local.json. Under "llm.models", fill in the host and model of the local entry. Under "llm.routes", set "default": "local". Now proofs run parity uses that endpoint. For a hosted OpenAI-compatible service, fill in openai_compatible instead, including api_key_env, and make it the default. Unused entries and routes can stay blank.

You can give particular jobs a different model. Below are the two routing keys for a setup where a local model plans and a hosted model writes and checks proofs. extract converts an ill-formatted reply to JSON; compact summarizes reasoning when a reply runs out of room. Unless routed separately, these stages use the role’s own model. 

{
  "llm.models": {
    "local": {
      "host": "http://localhost:8080/v1",
      "model": "qwen3-32b",
      "ctx_budget": 65536
    },
    "strong": {
      "backend": "anthropic",
      "model": "claude-opus-4-6",
      "api_key_env": "ANTHROPIC_API_KEY",
      "effort": "high",
      "ctx_budget": 200000
    }
  },
  "llm.routes": {
    "default": "local",
    "prover": "strong",
    "verifier_*": "strong",
    "extract": "local",
    "compact": "local",
    "fallback": "local"
  }
}
API Keys Stay Out of Config Files

Put the name of an environment variable in api_key_env, never the key itself. For the example above, export ANTHROPIC_API_KEY in the shell that starts Proofs. Proofs refuses an inline api_key field; even a gitignored file can end up in a backup or archive.

  • One-off changes: The conjecture’s local file overrides the workspace’s. CLI model flags replace the default, not roles explicitly routed elsewhere. With the entries above, adding --route prover=local changes just the prover for this command.
  • Verifier consistency: each certificate names one verifying model. In this example, "verifier_*": "strong" routes the three numbered verifiers to strong. The unrouted coding_verifier follows them. If you explicitly assign different models to two verifiers, the run stops at startup.
  • Per-call fallback (--with-fallback): if a model exhausts quota or fails all retries, that single call fails over to llm.routes.fallback (or default). The next call tries its primary model again; a verification check restarts cleanly on the fallback so its certificate names one model.

Context Limits

A model’s context window has to fit both the question (including earlier lemmas) and its answer. --ctx-budget TOKENS, or ctx_budget on a named model, sets their combined budget for one call. It does not enlarge the model’s window. Where the server reports a lower limit, Proofs uses that instead.

  • Reading an answer: Agents are asked for JSON. Proofs first parses the reply locally. For a role such as the planner, it can make an extract call if the reply does not parse. The prover is an exception: Proofs keeps its text rather than asking another model to rephrase a proof.
  • Continuing a partial answer: if a reply reaches the token limit, Proofs summarizes the model’s reasoning but keeps the answer so far word for word. The model can then continue where it stopped. llm.max_compaction_passes limits how often this can happen (default 2).
  • If the proof still does not fit: the reviser uses the summary and partial proof to suggest a smaller lemma or correct the statement.
  • If the server refuses the request: A context-length error with a reported ceiling is not a truncated answer. Set the budget to that ceiling and resume. If the prompt alone is too large, reduce the lemma window or use a model with more room; retrying the same request won’t help.
