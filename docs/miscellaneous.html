Miscellaneous

Most conjectures can start with just a statement. Add a tool when an argument needs an exact computation, a reference when there is a published result worth citing, or a planner note when you have an idea but not a proof. None is required for the first run.

Declaring Tools

By default the prover writes text; it can look up lemmas but cannot execute a script. Use --tools python, --tools sage, or --tools all to let the prover, reviser, and verifiers call run_code with tools declared by this conjecture. The flag does not install anything. Each script starts in a fresh process: it cannot depend on a variable left over from an earlier calculation.

Declaring tool versions (flake.nix & tools.lock)

The maintainer declares the environment in a flake.nix beside conjecture.md. This is a different flake from the one that installs Proofs: it describes what the mathematics may rely on. This example provides Sage and Python with SymPy on x86_64-linux; choose the appropriate system for your environment. 

{
  inputs.nixpkgs.url = "github:NixOS/nixpkgs/nixos-unstable";
  outputs = { self, nixpkgs }:
    let
      system = "x86_64-linux";
      pkgs = nixpkgs.legacyPackages.${system};
      python = pkgs.python3.withPackages (ps: [ ps.sympy ]);
    in {
      devShells.${system}.default = pkgs.mkShell { packages = [ pkgs.sage python ]; };
      proofsTools = {
        tools = {
          sage.version = pkgs.sage.version;
          python.version = pkgs.python3.version;
          python.packages.sympy = pkgs.python3Packages.sympy.version;
        };
        policy.result_bytes = 65536;
      };
    };
}

After adding the flake (stage it first if using Git), run proofs tools lock parity from the workspace and commit the flake and lock files. A collaborator needs the declared executables on PATH at the matching versions, not Nix itself. proofs tools check parity checks those executables and tries the sandbox. If you use nix develop ./conjectures/parity to supply them, review the flake first: its shell hook runs outside the script sandbox.

The computation contract (coding.md & coding_verifier.md)

The proof must explain why a finite calculation settles its claim. For example, testing a hundred squares does not prove the parity conjecture. But once the proof shows that the parity of a square depends only on the residue modulo 2, checking both residues is exhaustive. A Python script for that step could be: 

for r in range(2):
    assert (r * r) % 2 == r
print('RESULT: {"residues_checked": 2}')
  • Every script puts its checks in assert statements and ends by printing exactly one line RESULT: <json> (bounded by policy.result_bytes, default 64 KB).
  • Provers cite computations in prose as [code:<id>] and list them in code_runs. Proofs reads the script and its RESULT from the run’s scratch directory rather than trusting the model’s account. It saves the script in code/<user>/<run>/<sha256>.<ext> and the execution record in computations/. Both the script hash and the result contribute to the lemma’s Merkle hash.
  • A fourth verifier (coding_verifier.md) audits the mathematical reduction, loop bounds, exact arithmetic (ZZ, QQ, finite fields—no floating point, no proof=False or Monte Carlo claims), and assertions.
  • Verifiers may run code only to justify a rejection (e.g., finding a counterexample to a step), never to excuse an incomplete proof.
  • To reproduce a cited script, use proofs verify parity LEMMA_ID --tools python --run-code for the Python example (substitute the ID from the graph; use --tools sage for Sage scripts). Read the displayed script before confirming. A failed assertion or a different RESULT writes a refutation; running out of local resources is inconclusive.

Sandbox & machine limits

The CLI needs to reach a model server, but a script checking two residues does not need the network, your API keys, or access to your papers. On Linux, a run with --tools uses bubblewrap to separate these permissions:

  • Outer sandbox (proofs itself): retains network access for LLM APIs, sees the filesystem read-only with $HOME hidden (except its config and package code), and writes only inside the workspace.
  • Inner sandbox (per script): A script has a temporary working directory, no network, and no access to your home or workspace. It gets a minimal environment, not your shell’s API keys, and runs in an isolated PID namespace so a timeout can stop its children too.
  • On macOS: Proofs uses sandbox-exec for each script, without an outer sandbox for the CLI. This backend has not yet been tested on a Mac. On Windows, use WSL 2 and check that bubblewrap can start in your distribution.
  • If the sandbox check fails, you can still run without --tools. Do not treat --unsandboxed-code as an installation fix: it lets model-written scripts run with your own file and network access.

A shared tool version does not imply a shared memory budget. Run proofs limits parity to see this machine’s limits and where each came from. If the requested jobs and their memory plus the reserve exceed physical RAM, reduce code.jobs or code.memory in the gitignored .proofs-local.json. Leave enough reserve for a local model server.

KeyDefaultMeaning

Lemma Window Strategies

The graph can grow far larger than a model’s prompt. The lemma window selects which usable statements an agent sees up front; it does not delete or invalidate anything outside it. Start with recent to build on the latest work, try relevance to surface an older result related to the target, or use breadth to explore less similar lines of argument. --strategy chooses the rule and --window-size N the size (default 30, -1 for all that fit). Proofs shrinks the selection when it needs room for the answer.

StrategySelection Rule
recent (default) The --lemmas-all newest lemmas (anyone's) plus your --my-lemmas newest (default ⌊N/2⌋ each, deduplicated) ordered by proved_at.
random,BETA Depth-weighted random sample with weight (depth + 1)β/(1-β): β = 0 is uniform, β = 1 picks the deepest lemmas.
depth,JITTER Focuses on sinks (lemmas no unsuspended lemma cites yet): jitter = 0 takes the deepest sinks; jitter = 1 samples sinks uniformly.
breadth Picks one sink at a time, favoring those with the fewest ancestors in common with earlier picks. MinHash estimates the overlap; numpy speeds up the estimate if installed.
relevance Queries the in-memory FTS5 search index against the lemma being proved (prover/reviser), the latest plan (planner), or the conjecture.
popular Lemmas cited by the most unsuspended lemmas.

Search & lookup tools

A small window need not strand a useful lemma. An agent can search for a result by topic, then look up a hit by ID to get its exact statement and check its hypotheses. These are read-only graph tools; you do not need to enable --tools python or give the model a shell. With --tool-mode auto, Proofs tries the server’s native tool calls first and switches to JSON if the server refuses them:

  • search_lemmas: searches all unsuspended lemmas outside the prompt using an in-memory SQLite FTS5 BM25 index (built in the background on first use and updated live on commit). Supports phrase/word queries, citation traversal via cites and cited_by, and pagination (capped at tools.max_search, default 5).
  • lookup_lemmas: reads full lemma statements by ID—for chasing citations in cited_lemmas or inspecting search hits (up to tools.max_lookup, default 10 per call).

Private Planner Comments (comments.md)

To steer the parity run, you might put “Try the contrapositive: what can the square of an odd integer look like?” in conjectures/parity/comments.md. The planner reads the notes at startup and weighs them as suggestions, not hypotheses it can assume. Restart the run to pick up edits. “Private” means Git ignores the file: its text is still sent to the planner’s model. It is not sent to the prover, reviser, or verifiers.

References & proofs parse

If a proof should be able to cite a theorem from the literature, a hint in comments.md is not enough. Put the source text (for example .tex, .md, or .txt, not a PDF) in the conjecture’s references/ directory. As maintainer, run proofs parse parity with your model route or flags. The parser sends the sources to its model and extracts individual statements, not whole papers.

Review the extracted hypotheses and source locations against the original before committing references.md. Despite its name it contains a JSON array. Collaborators pull this file, not your gitignored source directory, and do not need to rerun the parser.

  • Stable citations: the parser assigns each result an ID such as ref_1. Parsing again reuses the ID when the formal statement matches and does not remove earlier results.
  • Who sees what: for collections under 100 entries, planners and revisers see a short description (slogan) and ID for each result. Provers see the formal statements and list their sources in cited_references. Verifiers see the statements of the cited references only.
