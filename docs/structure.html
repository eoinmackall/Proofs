Structure

A run does not ask for the whole proof in one answer. It starts from the claim in conjecture.md and tries to establish smaller claims, called lemmas. Each accepted lemma can cite earlier ones. These statements and citations form a directed acyclic graph (DAG): follow a proof’s citations far enough and you reach its starting points, not the proof you started from.

The Pipeline

Take the parity conjecture: if an integer’s square is even, the integer is even. A useful lemma would be “the square of an odd integer is odd.” A prover could write the integer as 2k + 1 and expand its square. Once that argument passes review, a later proof can cite the lemma and take its contrapositive instead of repeating the algebra.

Here is one iteration of a serial run. An agent is a role with a particular prompt, not necessarily a different model. The models propose the mathematics; Proofs assigns the IDs, checks that citations exist, and writes the records.

  1. Planner (planner.md): reads the conjecture, a selection of usable lemmas, and recent unsuccessful attempts. It proposes five possible next steps toward a proof or a counterexample. Each gets an ID now, but none is evidence yet: one candidate cannot assume another candidate is true.
  2. Selection: in --mode auto, a serial run picks one candidate uniformly at random. Parallel workers take the oldest available candidate from a shared queue. In manual mode, you choose from a menu.
  3. Prover (prover.md): drafts a proof and lists the lemmas (cited_lemmas), references (cited_references), and optional computations (code_runs) it relies on. Proofs checks the citations first. If one is unknown or suspended, the proof goes back to the prover.
  4. Verifiers: the same model reviews the proof with three different prompts:
    • verifier_1: overall logical soundness and computations.
    • verifier_2: definitions, citation fidelity, and exact match to the target conclusion.
    • verifier_3: algebraic manipulations, inequalities, edge cases, and case completeness.
    • coding_verifier.md (4th check): added automatically when a proof rests on run_code scripts.
    Each check sees the draft and the statements it cites, not the proofs of those statements. A single rejection sends the objection to the reviser. If all checks pass, Proofs records a certificate and saves the lemma in the graph. A “commit” in the run log means this write, not a Git commit.
  5. Reviser (reviser.md): reviews a rejected proof, or a partial proof that reached the context limit, and chooses one of three actions:
    • keep — keep the statement and tell the prover how to address each objection.
    • revise_statement — concrete evidence shows the statement is false or badly posed; rewrite it cleanly under the same ID.
    • new_lemma — try a smaller lemma first, with a new ID and a fresh attempt budget.
    After run.max_proof_attempts rounds without acceptance (three by default), the planner sees the statement on its reject list and can try a different route. Rejecting a draft is not a disproof of the statement.

Settling a Conjecture

A useful lemma need not settle the original question. Even if the planner says “we’re done,” Proofs looks for an accepted proof of the actual target. It computes the answer from the current graph:

  • A candidate can request "settles": "conjecture". Proofs pins its statement to the text in conjecture.md, so the reviser cannot weaken it to get a proof through. For conjecture_negation, the pinned text asks for an explicit counterexample and proof that it is one. You can request either target as a statement in manual mode.
  • The candidate gets the same review as any other. The run stops as settled if someone’s usable lemma states the pinned text (apart from whitespace normalization) and its dependencies are usable all the way down.
  • If the target changes or its only proof relies on a now-refuted lemma, the question is open again. If the graph supports both outcomes, Proofs warns rather than choosing one.

Checkpointing & Resuming

You can stop a long run without losing the lemmas it has already added. Those belong to the conjecture. Work in progress belongs to the run: its local checkpoints/<user_id>/<run_id>/ holds the plan, the stage reached on each unfinished lemma, and any completed verifier verdicts. The run ID is the 16-digit hex string in the startup banner.

  • Pause and continue: Press Ctrl-C once and let Proofs finish any commit in progress. Repeat your run command to continue from the checkpoint. The iteration count continues too: if you stopped at --max-iterations 1, raise the limit to do more work.
  • Choose a run: By default Proofs resumes your latest checkpoint for this conjecture. If another process holds its lock, a new run starts alongside it. Use --resume RUN_ID to select a particular checkpoint, or --fresh for a new plan and budget. Neither clears the shared graph.
  • Switch models: A saved proof keeps the name of the model that wrote it. A completed verifier step can be reused only if the proof hash and verifying model still match; otherwise that step runs again.

Bring Your Own Model

You don’t need a team of servers to run a team of agents. One local or hosted model can take each role in turn; the planner and the prover behave differently because they receive different instructions and evidence. Use separate models when there is a reason to, for example to reserve an expensive model for proof writing and review.

  • Set a default: --host and --model select the model for every role not routed elsewhere. To reuse that choice or assign a role to another model, set the routes in .proofs-local.json. See Backends & Routing for a working example.
  • Separate author from reviewer: A lemma records the model that wrote the proof; a certificate or refutation records the model that reviewed it. The verifier prompts must all go to the same model so that each certificate names one reviewer model. Collaborators can check it again with their own.
  • Allow a substitute: --with-fallback lets a call try a different configured model if its usual endpoint exhausts quota or retries. This is a choice for that call, not a permanent change of reviewer.
Bring Your Own Prompts, Too

For a hint like “try the contrapositive,” use comments.md. To change the prover’s instructions themselves, copy proofs/agents/prover.md into the conjecture directory beside conjecture.md and edit that copy. It replaces the default prompt for this conjecture only.

Parallel Mode (--parallel N)

Start in serial mode to follow one argument. If your endpoint can serve several requests at once, --parallel N lets workers pursue different lemmas on the same conjecture. An acceptance by one worker becomes available to the others. Planning and generation count toward the same cap of N simultaneous calls; a free worker takes the first task that’s due:

  1. Plan (parallel_planner.md): writes a strategic summary and ordered priorities at startup, on operator replan, or every run.replan_every (default 5) commits—always from scratch from the current DAG and reject list.
  2. Generate (parallel_lemma_generator.md): restocks the shared buffer with up to k fresh candidate lemmas, reserving slots before calling the model so concurrent generators never overflow the buffer.
  3. Prove: claims the oldest unclaimed lemma under lock and runs the exact same proof engine as serial mode.

With a default model route configured, try two iterations per worker. Otherwise append the same model flags as for a serial run.

proofs run parity --parallel 4 --max-iterations 2

The N+2k Buffer & Coding Loops

  • The buffer has room for the N lemmas being worked on and two batches of waiting candidates. For example, at a 64K context budget with four workers, a batch has four lemmas: twelve slots in total. Batch size k adjusts with the context budget and never exceeds N. A worker’s claim on a slot prevents another worker proving the same candidate.
  • Model concurrency and code execution have separate limits. With --parallel 4, --tools python, and one available code.jobs slot, only one worker can run scripts. That coding loop takes candidates marked "computation": true; the other three can still work on ordinary arguments.
  • Each worker has its own iteration budget. They share the list of rejected lemmas so the next planning step can avoid an approach another worker already tried.

Manual Mode

Use --mode manual when you have a route in mind and don’t want the next step chosen at random. You take over selection, not verification. For instance, if candidate 2 is the odd-square lemma, 2p asks the prover to write its proof; 2 means you will supply the proof yourself. If a verifier rejects your proof, you see the objection and return to the menu; nothing is added.

In a terminal, press h during a model call to switch modes at the next selection. At the menu, type a to return to automatic selection. Use --hotkey '' to disable the listener. With --parallel 3 --mode manual, only worker 0 pauses for you; the others keep working.

  • 1–9: prove that candidate yourself—paste or type your proof (bracketed-paste supported; Alt+Enter or Ctrl+J for newlines, Enter submits) and supply citations as comma-separated IDs or prover JSON. Your proof goes through the exact same three verifiers before entering the DAG.
  • 1p–9p: ask the prover to tackle that candidate.
  • w / wp: write your own lemma statement and either prove it yourself (w) or hand it to the prover (wp).
  • r: discard the shortlist and send the planner back with optional notes.
  • q: save the checkpoint cleanly and exit.
